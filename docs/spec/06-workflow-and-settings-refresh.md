# 06 — Workflow, organization map, reporting, agents, and settings refresh

**Status:** Reviewed and assigned for implementation on 2026-10-05. Track completed changes below. Keyboard shortcuts are in spec 07.

Reduce friction in contact entry and day-to-day work, make every workspace view linkable, improve the organization map and quote library, add a report workflow, and simplify team and agent settings. Preserve the Anvinn-derived design tokens and generic UI components. This is a behavioral and layout change, not a visual-system replacement.

The current app is a single TanStack route with in-memory page selection; only some contact-search navigation writes query parameters. The board has page-height columns; the organization map uses a top-down hierarchy with a toolbar; the quote library uses equal-height grid rows. Contact, organization, AI, and MCP data are backed by team-scoped API routes and SQL tables. The existing contact-log YAML and Typst file are export examples, while the LOI has a separate configurable Typst template. These observations describe the current code, not desired behavior.

## A. Navigation and daily work

1. **Linkable views.** The URL must identify the selected team and every workspace destination: home board/list, contact detail, `Sist kontaktet`, search, duplicates, organization map and its selected domain or organization, `Sitater`, profile, team settings, and class settings. It must preserve meaningful page state such as search text, board filters/sort/layout, and the selected activity or highlighted search passage. Refresh, copied links, browser Back/Forward, and opening a link in another tab must restore the same view. Reject invalid or unauthorized parameters gracefully and show a valid fallback. Local-only drafts may stay in local storage. Keep existing contact/activity links working or redirect them to the canonical form.
2. **Phone action.** Starting a phone call on a contact must display that contact's saved phone number prominently, with a copy button and clear copied feedback, while the call composer/timer is active. If no number exists, show an explicit missing-number state without blocking call logging. Copy must copy the displayed number. For missed calls, make the reminder field optional: remove the required `Hopp over` choice and allow saving while the field is untouched. Use the visual style of the existing post-conversation status choices for the final save/status actions. The save-without-status-change action has no icon.
3. **Board.** The Kanban board fills the remaining viewport height. Each status column has its own vertical scroll; the board retains horizontal scroll. Headers and counts stay visible while their cards scroll. Drag-and-drop, edge scrolling, new-contact highlight/scroll, and reduced-motion behavior must still work across both scroll axes. On narrow screens, the board remains usable without trapping page or keyboard scrolling.
4. **`Sist kontaktet`.** Align the assignee dropdown and other header controls on all supported widths. Opened menus must anchor to their triggers and stay within the viewport. Keep the existing feed content and filtering behavior.
5. **Duplicates navigation.** Show `Duplikate kontakter` in the sidebar and command palette only if the active team has at least one confirmed duplicate. A saved direct link to the duplicates view may still show its empty state after the last duplicate is removed.
6. **Quote library.** Lay out `Sitater` as a responsive masonry grid so variable-length cards pack vertically without row-height gaps. Preserve source, stale/deleted indicators, search, open-source action, and removal; keep a single reading order for keyboard and screen-reader navigation.
7. **Sidebar.** Remove the separate clipboard-paste button beside `Ny kontakt`. The `Ny kontakt` action itself remains. Clipboard text can still be pasted into the creation flow if that flow supports it. Rename `Hjem` to `Kontaktlogg`. Place `Duplikate kontakter` alongside the other contact destinations when it is visible. Remove the displayed `Kontakter` and `Oversikt` section headings.
8. **Sidebar inbox.** Clicking the `Innboks` button opens a flyout attached to the sidebar's right edge instead of a centered dialog. The command-palette Inbox action and the `i` shortcut from spec 07 open the same flyout. Keep its count, reminders, inbound email suggestions, cross-team requests, and empty state. When the actionable item count is zero, render the Inbox button without its prominent outline and do not show a `0` count pill; when the count is positive, give the button its outlined/emphasized treatment and show the count. Count due reminders, inbound suggestions, access requests, and class-admin inbox items as the current button does. The flyout has its own scrolling, does not resize the sidebar or require a modal backdrop, and closes from the button, Escape, or navigation to another destination. On narrow screens it must fit the viewport without becoming inaccessible or pushing content off-screen.
9. **Dark sidebar edge.** In dark mode, remove the visible border/shadow outline on the sidebar's top, bottom, and left edges. Keep the right-side separation from main content as needed. Apply this only to the sidebar, leaving the shared `.glass` styling of dialogs, menus, and other components and the light-mode sidebar unchanged.

The Linear-like shortcut system is in [spec 07](07-keyboard-shortcuts.md). The existing ⌘K/Ctrl+K palette continues to work in this unit.

**Acceptance examples:** A copied `Sist kontaktet` link survives refresh with its filter; dragging a card near the bottom of a full-height column scrolls that column; a team with zero duplicates has no duplicates navigation item; a call with a saved number exposes a one-click copy action; Inbox opens from the sidebar without a modal backdrop, appears quiet at zero items, and becomes outlined when an item arrives; the dark sidebar has no top, bottom, or left outline.

## B. Contacts and inline AI

1. **Simpler person model.** A contact links directly to one organization. Retire the contact `departmentId` relation and `position` field throughout UI, API, MCP tools, AI extraction, search, graph, duplicate comparison, exports, and documentation. Keep the existing organization and domain concepts. `Kort beskrivelse` captures a person's role, function, or relevant context. This workspace is not yet in production or active use, so the schema migration does not need a lossless backfill of existing position/department values.
2. **New contact form and organization selection.** Initially show name, organization, email, and phone. Hide `Kort beskrivelse` and person tags from this form; they remain editable on the contact page. There is no position or department input. Keep `Legg til` and `Legg til og åpne`, organization reuse/create, and pasted-text extraction behavior. On contact detail, make the organization field a combobox that can also create a new organization inline; the current select cannot do this.
3. **Description generation.** Rewrite the person-description prompt to produce a concise Norwegian phrase grounded in known evidence, prioritizing role or function and useful professional context. Examples of the intended style: `Instituttleder for biokjemisk avdeling`, `Erfaren fisker ved Rana oppdrettsanlegg`, `Senior fullstackutvikler, spesialiserer seg på apputvikling`. Avoid unsupported personal judgments, generic praise, and invented titles. If evidence is insufficient, produce no suggestion. Review representative outputs before enabling automatic application.
4. **Inline AI suggestions.** Remove the standalone `AI-forslag` card from contact detail. Display pending suggestions under the field they affect: email, phone, organization, description, person tags, domains, and `stikkord` where applicable. Each suggestion shows its proposed value and source evidence and has accept/dismiss controls. Stale suggestions must not apply silently; editing a field must not accidentally accept a suggestion. Keep per-contact AI permission, manual generation access, and the existing audit/restore behavior in an appropriate location. In safe-auto mode, continue extracting evidence for filled fields: automatically fill supported blank fields, but show a suggestion for a different value when a field is already filled instead of overwriting it. Drop a suggestion if its value equals the current value after trimming and case folding. This replaces the older safe-auto rule that stopped extraction once a field was filled.
5. **Conversation-based contact recommendation.** From eligible call, meeting, or email text, AI may recommend contacting another named person when the conversation contains concrete evidence. Show the source passage and why the person was mentioned. Check the active team's existing contacts before proposing creation; link to an existing match when plausible. Accept opens a prefilled, editable new-contact form; dismiss suppresses that recommendation for the source version. Never create the person automatically. Follow existing external-AI permissions and exclude blocked activity context and research notes. When a suggested contact is created, add `Referert til av <source contact name>` with a link back to the source contact in its Markdown information section; keep the link tied to the source contact ID so renames do not break it.
6. **Tilleggsinformasjon.** MCP contact creation may attach Markdown information about the person in a separate, editable `Tilleggsinformasjon` section on contact detail. Render it as sanitized Markdown with a clear source label. Keep it distinct from the team's shared note and the activity timeline; do not display it as a message. Include it in local search and in MCP contact reads, so a connected agent may use it as context. Exclude it from built-in AI features and deterministic export. Contac-generated referral backlinks may also appear here with their own source label.

**Acceptance examples:** A new contact requires only name and organization; an AI phone suggestion can be accepted under the phone field; a filled phone field receives a different pending suggestion in safe-auto mode but is not overwritten; a recommended person already in the team is linked instead of duplicated.

## C. Organization map and group summaries

1. **Map canvas.** Replace the current top-down hierarchy with an automatically arranged outward organization map. Keep visible links between domains, organizations, and contacts. Show all domains by default. Give the map the available viewport height and width. Users can drag empty background to pan in any direction; two-dimensional trackpad scrolling and pointer/touch interaction must allow reaching nodes beyond every edge. Nodes are not manually positioned. Node clicks must not trigger background panning. Provide a reset/fit action and keyboard-accessible routes to nodes.
2. **Focused domain state.** Remove the top toolbar controls. Selecting a domain focuses its connected organizations and contacts. In that state, show a back arrow at the top left labeled `Vis alt`; it restores the complete map. Organization and contact detail popovers and in-place domain editing/creation remain accessible without a global CRUD settings page. Loading a domain or organization map URL restores its focus.
3. **Direct organization relationships and popovers.** With departments retired, connect a contact directly to its organization. Keep one organization record and one contact node even when several domains connect to the same organization. Preserve consistent domain colors and clear links. Show each contact's complete short description under their name, wrapping it instead of truncating it. The contact popover shows name, short description, person tags, and status; it does not need contact information. Increase the contrast and selected state of domain chips in the organization popover.
4. **Organization status.** Put the status dropdown to the right of the organization name, without a `Status` label. The choices are no status, `Kunde`, `Konkurrent`, and `Samarbeidspartner`. Give each nonempty status a distinct color from the existing palette and apply it to the organization node without obscuring domain link colors; no status uses the neutral node style. Replace the old organization status enum and its default; a new organization starts with no status. A signed LOI remains recorded on the LOI itself and no longer suggests or requires an organization-status change.
5. **Group summary.** Rename `Viktigste funn` to `Oppsummer samtaler`. Repair generation for both organizations and domains; the current domain view can report `0 kontakter` despite linked contacts. Display the actual number of linked, nonduplicate contacts separately from the number of contacts with eligible AI conversations. Include each eligible linked conversation once, respect AI exclusions, and report when none are eligible. A saved summary may be stale when sources change; regenerating remains a deliberate click. Add regression cases for an organization and a domain with multiple contacts, a shared activity, and an excluded activity.

**Acceptance examples:** A user can pan from a far-left domain to a far-right organization by dragging the background; selecting a domain leaves only its related graph visible and shows the back button; a shared activity does not duplicate its text in an organization summary.

## D. Typst reporting and citations

1. **Permanent team-scoped contact number.** Assign each contact an immutable, monotonically increasing integer within its team. Allocation must be safe under concurrent creation and have a unique `(team, number)` constraint. Existing contacts receive deterministic backfilled numbers; historical duplicates keep numbers, and deleted numbers are never reused. This number is a reference label, while UUID remains the internal key. Show the number where it helps identify a contact and include it in API and export data.
2. **Standard report template.** Offer a downloadable, versioned Typst report ZIP independent of the LOI template. The developer will upload the ZIP later to the private Supabase Storage bucket `workspace-files` at the exact object key `report-templates/contac-report-v1.zip`. The app may point to this currently nonexistent object; show a clear unavailable message until it has been uploaded. The ZIP must include or document the files needed for contact references and the contact-log table. Copied snippets must compile against the supplied version. There is no team setting to edit this template.
3. **Quote citation.** Each usable quote shows `Kopier Typst-sitat` without a separate Typst-mode toggle. The report citation macro is `#cite-contact(1, 2, ...)`, using permanent team-scoped contact numbers. A single-source quote normally uses `#cite-contact(1)`, and multiple contacts may be cited together. The copied snippet includes the quote, its contact number citation, and source metadata sufficient to locate the original activity or note. A quote with a deleted source or missing contact shows a clear unavailable state. Validate the complete snippet against the ZIP after the developer uploads it.
4. **Contact-log export.** Offer `Kopier kontaktlogg som YAML` from a team-level reporting/export location. Copy the complete deterministic team log for pasting into a file used by the report template. Preserve the one-activity-once rule, all linked contacts, timestamps, transcript/summary, and attachment metadata. Include team-scoped contact numbers. Remove `Vis full kontaktlogg` and `Last ned YAML` from contact detail. Clipboard copy replaces YAML download; no new download location is needed.
5. **LOI setting.** Remove team editing/import of the LOI `Typst-mal`; use the built-in LOI source for future LOIs. Existing sent/generated PDF versions remain unchanged. This pre-production workspace does not need a separate migration path for customized team templates.

**Acceptance examples:** Concurrent creations in one team get different numbers; the same number may exist in two teams; a copied quote snippet compiles in the downloaded report template; a shared meeting appears once in the copied YAML; old LOI PDFs remain accessible.

## E. Agent access and MCP

1. **Personal entry point.** Move `Agenttilgang` from team settings to each user's profile. A user selects exactly one active team for their agent access. Changing that selection immediately switches existing Claude and Codex connections to the new team; the next request must check current membership and the current selection. Show the active team and allow the user to revoke their own connection. Previously copied agent instructions still contain the old expected team ID and therefore cause the required mismatch stop until regenerated.
2. **Simpler connection.** Replace the named team-token creation flow with a user-authenticated install/connection path for Claude and Codex in the first release. Verify the actual client setup before promising one-click installation. Remove old named tokens and OAuth grants as part of the same pre-production change, with no migration window. Never expose an old secret in the UI. Preserve the current MCP write boundary unless this spec explicitly extends it.
3. **Verify team identity.** Add a read-only MCP `get_team_identity` tool. It returns the immutable team ID and current workspace team name resolved from the authenticated connection, without accepting a caller-supplied team ID. This name comes from the team picker, not the optional product/LOI name. The profile connection UI shows that team ID and name. The copied agent instructions tell the agent to call this tool before any Contac contact read or write in a new conversation/session, compare its returned ID with the expected ID, and notify the user and stop using Contac if they differ or verification fails. Team name is a human-readable cross-check; a rename must not cause a false mismatch when the ID is correct. Data tools should also accept an `expectedTeamId` from the copied instructions and reject a mismatch before querying or writing data, so an accidental wrong-team connection cannot proceed if the initial check is skipped. Plan migration for existing MCP clients when making this argument mandatory.
4. **Copyable agent instructions.** Provide a Markdown block and one-click copy action for the selected team's `CLAUDE.md`, `AGENTS.md`, or equivalent agent instructions. Include the expected immutable team ID and current name, the mandatory identity check, a brief explanation of Contac and the team's scope, when to search for existing contacts, how to create contacts and activities, and what the agent cannot change. The copy must not include credentials or private tokens. Regenerate it when the selected team changes.

   The generated block must communicate this rule clearly: “Expected Contac team: `<team name>` (`<team UUID>`). Call `get_team_identity` before other Contac tools. If its team ID differs or the call fails, tell the user which team is connected, when known, and stop using Contac. Pass `<team UUID>` as `expectedTeamId` to subsequent data tools.” The angle-bracket values are filled from the selected team, never copied as literal placeholders.
5. **Batch contact creation.** Add a team-scoped MCP tool that accepts up to 100 contacts, validates each against the simplified contact schema, and reuses/creates organizations consistently. Process valid nonduplicates even if other items fail. Reuse the team's duplicate-matching rules to flag likely existing contacts for review instead of creating those items automatically. Return one result per input item: created contact ID, duplicate candidates, or a validation/write error, so the agent can retry or notify the user. One failing item must not cause an ambiguous response or cross-team write.
6. **MCP Markdown.** Both single and batch contact creation may include the agent-supplied Markdown described in unit B. The MCP tool descriptions must explain evidence, field limits, and the rule to search before creating a person.

**Acceptance examples:** A user connects an agent to Team A and cannot read Team B through that connection; `get_team_identity` reports Team A from the connection; instructions expecting Team B cause the agent to alert the user and stop before contact operations; revocation blocks the next MCP request; a batch reports which entries succeeded; copied agent instructions contain no access secret.

## F. Team settings, sharing, roles, and AI usage

1. **Order and names.** Put `Produkt/teamnavn` and logo first. This field edits the current LOI business name, not the underlying workspace team name; explain that distinction beside the field. When set, display this product name in place of `Contac` in the sidebar; otherwise keep `Contac`. Place invitations directly below. Then show ordinary AI controls and usage, followed by `Avanserte innstillinger` for model IDs and per-feature modes. Keep the OpenRouter credential reachable. Remove domain and person-tag CRUD sections from team settings; create/edit these at their points of use.
2. **Retire `Økter`.** Remove the team-settings card, navigation destination, session/check-in creation and summary workflow, and its AI feature control. There is no historical-session archive requirement for this pre-production workspace.
3. **External AI default.** Remove the team-level `Nye kontakter tillater ekstern AI som standard` option. New contacts default to allowed for external AI, while per-contact and per-activity blocks continue to work. This does not turn on any team AI feature or remove the OpenRouter token requirement.
4. **Usage.** Display the lifetime team total as `X tokens, USD x.xx brukt` in team settings. Aggregate on the server across all recorded calls, not only the last 100. Preserve a clear indication if some provider calls lack token or cost data; do not present a partial total as exact. Move/remove the redundant usage card on profile. No NOK conversion is needed.
5. **Automatic cross-team sharing.** Remove the `E-post og deling med andre team` card from team settings. Keep the actual inbound/Bcc behavior if still needed elsewhere. Automatically grant other teams read access to matching contact logs, including for existing teams whose checkbox is currently false. The scope remains matched contacts under the class-wide overlap rules; it does not grant browsing of all contacts in unrelated teams. Keep the shared contact note within its owning team. Remove the now-obsolete toggle from API/settings after migration.
6. **Flat team roles.** Remove the team `admin/member` distinction from invitations, labels, settings visibility, and API authorization. All team members can invite, change AI credentials and settings, and manage team settings. Personal agent connections remain controlled by their owning user, while each member can select a team they belong to. Existing owner/admin/member records and outstanding invitations must be migrated consistently; class-administrator authority and oversight remain distinct.

**Acceptance examples:** A new teammate can create an invite without choosing a role; team settings begin with product/team name and logo, then invite; AI model selection is inside `Avanserte innstillinger`; lifetime usage includes calls older than the latest 100; no team member loses contact access during role migration.
